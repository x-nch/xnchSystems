Command Interface
xnch-cli
Primary human entry point. Parses commands, renders structured output, manages session state, drives the simulation/confirm loop.
  • Parse intents into structured Command objects
  • Display plan diffs before execution
  • Manage TUI for multi-step workflows
  • Pipe raw events for scripting
Intent Parser
intent-svc
Converts raw CLI input or API calls into normalized Intent objects with action, target, context, and constraints.
  • Schema validation on inbound payloads
  • Ambiguity detection → confirmation prompts
  • Enrichment from memory context
Plan Compiler
planner
Decomposes an Intent into an ordered DAG of Task nodes. Handles dependencies, parallel branches, and rollback nodes.
  • DAG construction with topological sort
  • Resource conflict detection
  • Rollback path generation per task
  • Outputs serializable ExecutionPlan
Simulation Engine
sim-engine
Dry-runs the ExecutionPlan against a snapshot of current state. Produces a SimulationReport before any real action fires.
  • State snapshot at sim start
  • Mock tool execution with predicted outputs
  • Side-effect surface report
  • Risk score per task node
Executor
exec-runtime
Walks the confirmed DAG, dispatches tasks to agents or tools, handles concurrency, timeouts, and partial failures.
  • Concurrent task dispatch (asyncio)
  • Per-task timeout + circuit breaker
  • Emit ExecutionEvent to audit log on every state change
  • Pause/resume via control channel
Agent Registry
agent-reg
Catalog of available agents with capability manifests, health status, and resource requirements. Agents register on startup via gRPC.
  • Capability schema per agent (YAML manifest)
  • Health polling + deregistration on failure
  • Capability-based routing metadata
Agent Supervisor
supervisor
Manages agent lifecycle, enforces resource budgets (GPU memory, CPU, wall-clock), and kills runaway agents.
  • GPU VRAM budget enforcement via nvidia-ml-py
  • Watchdog timer per agent invocation
  • Restart policy (none / on-failure / always)
Model Adapter
model-adapter
Unified interface to local (vLLM/Ollama) and remote (Claude/GPT) models. Abstracts provider differences behind a single generate() call.
  • Provider enum: local_vllm / ollama / anthropic / openai
  • Fallback chain: local → remote
  • Token budget + streaming support
  • Prompt template registry
Nexi — Decision Engine NEW
nexi-engine
Policy-aware multi-option decision engine. Sits between Intent Parser and Plan Compiler. Does not generate a single answer — generates N candidate plans, evaluates them, and selects the best under current constraints and memory context.
  • Receives normalized Intent from Intent Parser
  • Loads context manifest from ctx-store via xnch /memory/read
  • Generates 3–7 candidate PlanOption objects via Model Adapter
  • Submits all options to xnch /policy/check in parallel
  • Scores surviving options → selects best → emits DecisionRecord
  • Submits DecisionRecord to xnch /verdict for final authorization
Option Generator NEW
nexi.generator
The only Nexi module that calls the Model Adapter. Submits a constrained generation prompt with a JSON output schema. Model returns N structured plan candidates — not prose, not a single answer.
  • Prompt is template-driven (versioned), not freeform
  • Output schema enforced via vLLM guided_json (logit masking)
  • Schema validation on response; retry once on failure
  • Fallback: rule-based option generator from policy memory
  • Model output treated as untrusted raw material
Policy Filter NEW
nexi.filter
Submits all generated options to xnch /policy/check in parallel before any scoring occurs. Drops BLOCK options immediately. Updates MODIFY options with xnch's corrected action spec.
  • asyncio.gather across all N options simultaneously
  • BLOCK → removed from candidate set
  • MODIFY → action_spec replaced, option flagged
  • DEFER → retained, marked for secondary auth
  • If all options blocked → escalate, never force select
Evaluator + Selector NEW
nexi.evaluator
Scores each policy-clean option across four dimensions. Applies intent-class-specific weight configs loaded from memory. Selects the highest-scoring option and assembles the full DecisionRecord.
  • policy_score: from xnch dry-run verdict quality
  • outcome_score: pattern match against episodic history
  • risk_score: reversibility + entity sensitivity + side effects
  • context_fit_score: structural coverage of intent constraints
  • Weights are versioned, adapted by learning layer over time
  • Confidence = score delta between top-2 options (stored in ledger)
Context Store
ctx-store
Structured relational memory. Not logs — typed entities: Decision, Observation, Constraint, Relationship. SQLite WAL mode.
  • Schema-versioned via Alembic
  • Entity graph (decisions → tasks → outcomes)
  • Foreign-key linkage to audit log events
Vector Index
vec-index
Semantic retrieval over structured memory. Embeddings generated locally (nomic-embed-text or bge-m3). Chroma as local ANN store.
  • Auto-embed on ctx-store writes
  • Hybrid retrieval: BM25 + ANN
  • Namespace isolation per agent/session
Episodic + Pattern Store NEW
outcome-store
Two new SQLite tables that power the feedback loop. Episodic store records every decision cycle with its outcome. Pattern store holds derived success-rate statistics extracted from episodic history.
  • Episode schema: intent_class, action_type, entity_class, outcome, prediction_delta
  • Episodes start PENDING, completed by execution outcome callback
  • Pattern extraction runs every 6h via APScheduler
  • Patterns: success_rate, confidence, observation_count, context_signature
  • Read by Nexi Evaluator for outcome_score computation
Learning Loop NEW
learn-loop
Background process that adapts Nexi's evaluation weights based on accumulated outcome history. No model training. No gradient updates. Pure statistical adaptation over structured episodic data.
  • Pattern Extractor: groups episodes, computes success_rate + confidence per (action_type, entity_class) tuple
  • Score Adapter: adjusts weight configs when dimension prediction accuracy < 0.6
  • Policy Candidate Generator: promotes high-confidence patterns to soft policy rules
  • All weight changes versioned, gated by operator review before activation
  • System improves by getting better at evaluating model output — model itself unchanged
Decision Ledger
ledger
Append-only, hash-chained record of every decision and execution event. Cannot be modified post-write. JSONL + SHA-256 chain. Now includes Nexi DecisionRecord with full option scoring breakdown.
  • Every ExecutionEvent signed with prev_hash
  • Integrity verification command
  • Selective export to JSON/CSV
  • NEW: DecisionRecord: options_generated, options_blocked, score breakdown, selected_option_id, confidence
Replay Engine
replay
Reconstruct system state at any point-in-time from the ledger. Also used for debugging and post-mortems.
  • Event sourcing: state = fold(events, initial)
  • Time-travel queries: xnch replay --at <ts>
  • Divergence detection vs current state

Data Flow UPDATED — 10 Steps

Flow: Input → xnch → Nexi → Model → Nexi → xnch → Simulation → Execution → Memory → Learning Loop
Step 1 · INGESTION
Input Ingestion
Human types command or external system POSTs to REST gateway. Raw input is wrapped in an InboundEvent{source, raw, ts, session_id} and pushed to the internal event bus (asyncio Queue or NATS JetStream).
POST /v1/intent {"raw": "deploy nexi-api to staging with canary 10%", "session_id": "s_abc123"}
Step 2 · CONTROL
Intent Parsing + Context Enrichment
Intent Parser classifies action type, extracts entities, pulls last-N relevant Decision and Constraint records from ctx-store via hybrid retrieval. Outputs normalized Intent{action, target, params, context_refs[]}. xnch resolves actor identity and pins system_state_version.
Intent{ action:"DEPLOY", target:"nexi-api", params:{env:"staging",canary:0.1}, actor_id:"pavan", actor_role:"OPERATOR", system_state_version:"v3.2" }
Step 3 · NEXI NEW
Context Manifest Load (Nexi → xnch → Memory)
Nexi calls xnch /memory/read. xnch queries episodic store, pattern store, and policy store in parallel. Returns a pinned context manifest: recent episodes for this entity class, active patterns with confidence scores, and all scoped policies. Nexi pins system_state_version — this snapshot is immutable for the session.
ContextManifest{ episodes: [last 20 DEPLOY × ML_MODEL outcomes], patterns: [{ action:"DEPLOY", entity:"k8s-svc", success_rate:0.78, confidence:0.64 }], policies: ["deploy.canary.max_pct_50", "deploy.require_sim_gate"] }
Step 4 · NEXI → MODEL NEW
Option Generation (Nexi → Model Adapter → vLLM)
Nexi constructs a constrained generation prompt using a versioned template. Calls Model Adapter → vLLM (RTX 3090). Output schema enforced via guided_json — model cannot produce malformed JSON. Returns 3–7 structured PlanOption candidates. Model output is untrusted raw material; Nexi does not surface it directly.
PlanOptions: [ A: { replicas:1, node:"gpu-01", canary_pct:10, resource_check:true }, B: { replicas:2, node:"auto", canary_pct:10, resource_check:true }, C: { replicas:1, node:"auto", canary_pct:25, resource_check:false }, D: { replicas:1, node:"gpu-01", canary_pct:5, resource_check:true }, E: { stage_only: true, no_traffic: true } ]
Step 5 · NEXI → XNCH NEW
Policy Filter — Parallel Dry-Run
Nexi fires GET /policy/check for all N options simultaneously via asyncio.gather. xnch evaluates each against the active policy set. BLOCK options are dropped. MODIFY options have their action_spec replaced with xnch's corrected version. If all options are blocked, Nexi escalates — it never forces a selection.
Verdicts: A→ALLOW B→ALLOW_WITH_WARNINGS C→MODIFY(resource_check forced true) D→ALLOW E→ALLOW Dropped: none Modified: C.resource_check patched to true by policy deploy.require_resource_check
Step 6 · NEXI EVALUATION NEW
Option Scoring + Decision Selection
Nexi evaluator scores each surviving option across 4 dimensions, weighted by intent class. Applies recency adjustment from episodic history. Outcome simulation runs if risk_score > 0.6 or action is irreversible. Selector picks highest composite score, assembles full DecisionRecord with scoring breakdown. Confidence = score delta between top-2 options.

Step 7 · XNCH AUTHORIZATION UPDATED
Final Verdict + Execution Token
Nexi submits the full DecisionRecord (not just the action) to xnch /verdict. xnch re-evaluates the selected action authoritatively, verifies system_state_version matches pinned version, emits audit record synchronously, and issues a signed RS256 execution token with TTL. The Plan Compiler then converts the selected PlanOption into an ExecutionPlan DAG.
Verdict{ verdict:"ALLOW", execution_token:"eyJ...", token_ttl_ms:30000, audit_ref:"aud_9f2a" } Plan{ id:"plan_xyz", nodes:[t1:k8s_deploy, t2:HumanGate(confirm canary?), t1_rb:k8s_rollback] }
Step 8 — Mandatory
Simulation + Diff Render
Sim Engine dry-runs the compiled plan. Mocked tool calls return predicted state deltas. CLI renders unified diff of current vs expected state. Risk score recomputed at plan level. Human must confirm or abort. Nexi's option selection has already pre-filtered high-risk plans — simulation acts as final human gate.
SimulationReport{ risk_score: 0.31, # Nexi pre-filtered; lower than v1 average side_effects: ["scales HPA to 3 replicas", "shifts 10% traffic"], flagged_tasks: [], predicted_state_delta: { canary_weight: 0.10, replicas: 1 }, nexi_confidence: 0.09 # score margin between Option A and B }
Step 9
Execution + Event Emission
After human confirmation, Executor validates the xnch execution token independently (RS256 + TTL check), then walks the DAG. Each task dispatched to Agent Supervisor → Tool Router → actual tool. Every state change emits an ExecutionEvent immediately appended to the Decision Ledger (hash-chained). Execution outcome (SUCCESS / FAILURE / PARTIAL) posted to xnch /execution/outcome.
Step 10 · LEARNING LOOP NEW
Memory Write-back + Feedback Signal
On execution completion, xnch completes the PENDING episode record in the episodic store. Nexi computes prediction_delta (predicted outcome_score vs actual outcome). If delta > 0.3, flags pattern for early re-extraction. Pattern extractor runs on schedule, updates success_rate + confidence for affected (action_type, entity_class) tuples. Score Adapter adjusts Nexi's evaluation weights if dimension prediction accuracy has drifted. ctx-store updated with new Decision entity. Vector index auto-embeds. Future sessions query this outcome immediately.
EpisodeCompleted{ outcome:"SUCCESS", prediction_delta: 0.21, early_extract: false } PatternUpdated{ action:"DEPLOY", entity:"k8s-svc", success_rate: 0.80←0.78, observations: 41 } # Next DEPLOY session: outcome_score for Option-A-class actions rises from 0.50 → 0.51 # After 50+ episodes: pattern confidence grows, Nexi ranking becomes self-reinforcing

Scoring Mechanism
learn.scoring
Every Nexi option is scored across 4 dimensions. Weights are versioned config, not hardcoded. The learning loop adapts weights per intent class based on which dimension best predicted real outcomes.
  • policy_score = xnch dry-run verdict (1.0 ALLOW → 0.3 DEFER)
  • outcome_score = pattern.success_rate × pattern.confidence (or 0.5 if no match)
  • risk_score = reversibility + entity_sensitivity + side_effect_count
  • context_fit_score = structural field coverage of intent constraints
  • composite = weighted sum; weights per intent_class from ~/.xnch/weights/weights_vN.json
Pattern Extraction
learn.extractor
Background job (APScheduler, every 6h) that groups completed episodes by (action_type, entity_class, intent_class) and computes outcome statistics. Creates or updates pattern records with updated success_rate and confidence.
  • Groups episodes with ≥ 5 observations per tuple
  • success_rate = SUCCESS / total (PARTIAL counts as 0.5)
  • confidence = min(1.0, count/50) × (1 − outcome_variance)
  • New patterns start as UNDER_REVIEW if confidence < 0.4
  • prediction_delta > 0.3 on any episode → triggers early extraction
Weight Adaptation
learn.weights
Every 100 completed episodes per intent class, the weight optimizer runs. It measures which scoring dimension best predicted actual outcomes, adjusts underperforming dimensions down, reinforces well-predicting ones. All changes are versioned and require operator review before activation.
  • If dimension prediction accuracy < 0.6 → weight −0.05, distribute delta
  • If prediction accuracy > 0.8 → weight +0.05, reduce from weakest
  • Minimum weight per dimension: 0.10 (no dimension goes blind)
  • Maximum weight per dimension: 0.55 (no dimension dominates)
  • Weight changes stored as versioned JSON, human-reviewable before activation
Policy Candidate Generation
learn.policy-gen
When a pattern reaches observation_count ≥ 50, success_rate ≥ 0.85, and confidence ≥ 0.75, the extractor generates a soft policy candidate. An operator reviews and may promote it to active policy. The derived policy then feeds back into xnch's policy filter — reinforcing the proven pattern further.
  • Policy class always starts as SOFT_GUIDANCE — never auto-promoted to BLOCK
  • Source pattern reference maintained for full traceability
  • Operator review gate: cannot activate without explicit approval
  • Once active: options aligned with derived policy score higher in policy_score
  • Creates self-reinforcing loop: good patterns → policy → better selection → more successes
Evolution Phases
Phase 1 — Cold Start (0–50 episodes): No patterns. outcome_score defaults to 0.5. System selects on policy + risk only. Conservative by design.
Phase 2 — Pattern Emergence (50–200): Patterns form. outcome_score begins differentiating options for known (action_type, entity_class) tuples. Recency adjustments activate.
Phase 3 — Weight Calibration (200+): Intent-class-specific scoring personalities develop. Composite score becomes an accurate predictor of execution outcomes.
Phase 4 — Policy Derivation (mature patterns): High-confidence patterns generate soft policy candidates. Operator-gated promotion. System begins preemptively favoring proven action structures.
Key principle: The model layer never changes. What improves is Nexi's ability to evaluate model output — the intelligence accumulates in the memory architecture, not the weights.

Failure Modes + Safeguards

Critical
Execution Without Simulation
Plan executes without a completed SimulationReport attached, bypassing the dry-run gate.
Safeguard: Executor refuses to start any plan where plan.sim_id == null or sim.status != COMPLETED. This is a hard check, not a flag.
Critical
Audit Log Corruption / Tampering
Ledger file modified post-write, breaking hash chain and invalidating audit trail.
Safeguard: xnch audit verify run on every startup. File mode 0400 post-append. Optional: rsync to secondary path on each write.
Critical
GPU OOM During Agent Execution
Agent loads model exceeding VRAM budget, crashing vLLM process and taking down other agents sharing the GPU.
Safeguard: Supervisor calls nvmlDeviceGetMemoryInfo before dispatching. Agent manifests declare min_vram_mb. Dispatch blocked if free VRAM < requirement + 10% headroom.
Warning
Partial Execution Leaving Inconsistent State
Network failure or crash after task T2 completes but before T3, with no rollback triggered.
Safeguard: Every mutating task has a rollback node in the DAG. On Executor startup, any plan in state RUNNING is auto-paused and flagged for human review. Rollback is explicit, not automatic.
Warning
Agent Infinite Loop / Runaway Cost
Agentic loop does not terminate, consuming tokens and CPU indefinitely.
Safeguard: Per-invocation wall-clock timeout (default: 120s, configurable). Max token budget per plan enforced by Model Adapter. Supervisor kills process on timeout, writes KILLED event to ledger.
Warning
Memory Drift — Stale Context Poisoning Plans
ctx-store returns outdated Decision records that were superseded, causing planner to build on invalid assumptions.
Safeguard: All Decision entities have valid_until field. Retrieval filters expired records. Planner logs all context_refs used; diffable in audit trail.
Informational
Simulation Divergence from Reality
Sim predicted state X but execution produced Y due to external state change between sim and exec.
Safeguard: Executor records actual vs predicted outcome per task. Divergence metric tracked in Prometheus. Replay Engine can diff sim vs actual post-hoc.
Informational
SQLite Write Contention
High-frequency concurrent writes from multiple agents saturate SQLite WAL, causing latency spikes.
Safeguard: WAL mode + PRAGMA busy_timeout=5000. Writes batched per-agent via write queue. If P99 > 50ms, escalate to DuckDB or Postgres.
