CRITICAL GAPS (Must Fix)

---
C-1. Scoring Dimension Name Schism

Location: learning-loop.md (Score Adapter monitoring) · audit.md (Decision
Ledger schema) · decision-model.md · data-contracts.md (Evaluated Option)

The system uses two incompatible naming schemes for the same four evaluation
dimensions:

┌──────────────────────────────────┬──────────────────────────────────────┐
│             Used in…             │           Dimension names            │
├──────────────────────────────────┼──────────────────────────────────────┤
│ decision-model.md,               │ policy_score, outcome_score,         │
│ data-contracts.md                │ risk_score, context_fit_score        │
├──────────────────────────────────┼──────────────────────────────────────┤
│ audit.md Decision Ledger         │ safety, efficiency, compliance,      │
│ dimension_scores                 │ context_fit                          │
├──────────────────────────────────┼──────────────────────────────────────┤
│ learning-loop.md Score Adapter   │ safety, efficiency, compliance,      │
│ monitoring config                │ context_fit                          │
└──────────────────────────────────┴──────────────────────────────────────┘

Impact: Three distinct failures:

1. The Decision Ledger records dimension scores under names that do not match
the scoring formula in decision-model.md. Decision reconstruction
(decision-model.md — Decision Reconstruction, step 3: "verify stored
composites match formula output") is impossible — the ledger fields don't
correspond to the formula's variables.
2. The Score Adapter monitors safety/efficiency/compliance dimension accuracy
but those dimensions don't exist in the evaluation pipeline. It is monitoring
phantom signals and will never detect real weight drift.
3. The weight configuration schema (implementation-contracts.md Contract 6)
uses policy_score, outcome_score, risk_score, context_fit_score — consistent
with decision-model — but this is directly inconsistent with the learning-loop
  monitoring config that governs when weights are updated.

C-2. Compiled DAG / action_spec Contradiction in Execution Dispatch

Location: system-loop.md (Step 10a, Step 11) · data-contracts.md (Execution
Dispatch Payload) · execution-flow.md (Step 11)

system-loop.md Step 10a states: "The compiled DAG (not the raw action_spec) is
  what the execution-runner receives." Step 11 confirms: "DAG walked in
topological order."

data-contracts.md Execution Dispatch Payload defines:
{
  "action_spec": { "type": "string", "target": "string", "params": {} }
}

This is a flat object, not a DAG. execution-flow.md Step 11 inline data
contract also shows action_spec (not a DAG).

No schema for the compiled DAG exists anywhere in the reference docs. The
execution-runner's DAG walking behavior (topological order, step_type,
retry_config, on_error policy per step — described in system-loop.md Step 10a)
  has no corresponding data contract.

Impact: The execution-runner cannot be implemented — its primary input type is
  undefined. The Execution Dispatch Payload would need to be redesigned or the
DAG spec would need to be added. Also: any schema validation at the runner
boundary is impossible without this definition.

C-3. DENY Verdict Used in Policy DSL Examples — Not in Defined Enum

Location: implementation-contracts.md Contract 1

The rule structure defines the verdict enum as: "ALLOW | ALLOW_WITH_WARNINGS |
  BLOCK | MODIFY | DEFER".

Two examples within the same contract use verdict: DENY:

- rule_id: "no-weekend-deploys"
  ...
  action:
    verdict: DENY   # not in enum

- rule_id: "require-admin-for-schema-change"
  ...
  action:
    verdict: DENY   # not in enum

Impact: The policy validator (which enforces the enum at load time) would
reject both example rules. Any operator who copies these examples into
production policy files gets a broken policy. The relationship between DENY
and BLOCK is undefined — they may be synonymous or DENY may be an
unimplemented fifth verdict type.

C-4. Pattern Extractor Grouping Tuple Is Inconsistent Across Three Documents

Location: implementation-contracts.md Contract 3 · memory-system.md ·
learning-loop.md

The tuple used to group episodes into patterns is defined three different
ways:

┌───────────────────────────────────────┬─────────────────────────────────┐
│                Source                 │         Grouping tuple          │
├───────────────────────────────────────┼─────────────────────────────────┤
│ implementation-contracts.md Contract  │ (intent_class, action_type,     │
│ 3 (Context Signature)                 │ entity_class, actor_role) — 4   │
│                                       │ fields                          │
├───────────────────────────────────────┼─────────────────────────────────┤
│                                       │ (intent_class, action_type,     │
│ learning-loop.md Pattern Extractor    │ entity_class) — 3 fields, no    │
│                                       │ actor_role                      │
├───────────────────────────────────────┼─────────────────────────────────┤
│ memory-system.md Pattern Extractor    │ (action_type, entity_class) — 2 │
│                                       │  fields only                    │
└───────────────────────────────────────┴─────────────────────────────────┘

Impact: The context_signature (SHA-256 hash) is computed by Contract 3 from 4
fields. If the Pattern Extractor groups by 2 or 3 fields, the patterns it
writes will carry context_signature values derived from a different tuple.
Lookups at Step 4 (manifest assembly) and Step 7 (outcome_score computation)
use the Contract 3 hash — they will produce zero matches against patterns
written with a different key. The learning loop produces patterns that are
invisible to the evaluator.

C-5. Episode Completion Written Twice — Steps 13 and 14

Location: execution-flow.md Step 13 · execution-flow.md Step 14 ·
system-loop.md Step 14

execution-flow.md Step 13 states: "xnch validates token ref matches a known
issued token. Writes outcome to episodic store (completes the PENDING episode 
record)."

execution-flow.md Step 14 states: "Nexi calls POST /memory/write on xnch with
outcome-enriched decision record" — with write_type: EPISODE_COMPLETION.

Both steps claim to complete the PENDING episode. The Step 14 code example
writes execution_outcome, outcome_delta, side_effects, prediction_delta,
early_reextraction_flag — fields that are not all present in the Step 13
write.

Impact: It is undefined which write is authoritative, what fields each write
contributes, whether xnch merges them or the second write overwrites the
first, and whether a Step 13 write failure (which halts further processing per
  the failure table) also prevents the Step 14 fields from ever being written.
prediction_delta and early_reextraction_flag — the two fields that drive
learning — appear only in the Step 14 payload. If Step 14 is a required second
  write, the failure handling at Step 14 (backoff, PENDING reconciliation)
applies to learning-critical fields that aren't protected by Step 13. The
write authority boundary is unresolved.

IMPORTANT RISKS (Should Fix)

---
R-1. Simulation Gap: Option #3 May Be Selected Without Forward Projection

Location: decision-model.md — When Simulation is Triggered · execution-flow.md
  Step 8

Simulation runs on "top 2 options only (by composite score before
simulation)." If simulation re-scores both of those options downward (risk +=
0.3), option #3 — which was below the simulation threshold — may rise to
become the highest-scoring option after re-ranking. It is then selected
without ever undergoing simulation.

Impact: An option that ranks #3 may have risk_score > 0.6 or reversible = 
false — exactly the conditions that triggered simulation for the top 2. The
system would select this option for real-world execution without the safety
gate that would have caught it. The trigger conditions for simulation are
per-option; skipping #3 because it was initially low-ranked does not make it
safer.

---
R-2. Execution Token TTL Expiry Under Runner Queue Contention

Location: runtime.md — Concurrency Model (execution-runner) ·
implementation-contracts.md Contract 2

runtime.md: "The runner handles one active execution at a time per process
instance." The execution token TTL is 30 seconds.

If two sessions both complete Step 10 and dispatch simultaneously, the second
session's token waits in the runner's queue. If the first execution takes more
  than 30 seconds (Step 13 latency: "5000–60000ms"), the second session's token
  expires before the runner processes it.

Impact: The second session receives TOKEN_EXPIRED and Nexi resubmits to Step
10 for a new token. The new token is issued, dispatched, and the runner may
again be busy. Under sustained load with multiple sessions in-flight, there is
  no documented queue depth limit, no timeout escalation, and no priority
mechanism. This is a potential livelock for concurrent execution requests that
  outnumber runner capacity.

---
R-3. Session TTL Expiry During Long Execution → Unresolvable Orphans

Location: implementation-contracts.md Contract 7 (Session Lifecycle) ·
execution-flow.md Step 13 · system-loop.md Failure Paths

Session TTL is 120 seconds from creation. The execution itself can take up to
60,000ms (60 seconds, Step 13). Pre-execution latency is up to 4,600ms. An
execution that runs near the maximum duration on a slow session startup could
have its outcome arrive after session expiry.

Contract 7 states: "If an execution was dispatched and the outcome has not
been received, xnch marks the execution reference as ORPHANED in the Decision
Ledger on cleanup."

Impact: The execution completed in the world — the real-world side effect
happened. But the outcome is never written to the Episodic Store. No episode
is completed. No pattern extraction is triggered. The system acted but cannot
learn from the action. No reconciliation process for orphaned executions is
defined anywhere (see Minor Observation M-6). This is a silent learning loop
break.

R-4. xnch Public Key Refresh Mechanism Is Undefined

Location: implementation-contracts.md Contract 2 (Execution Token JWT)

Contract 2: "public key published at GET /auth/public-key, refresh on 401 from
  xnch."

The execution-runner validates tokens "independently — does not trust Nexi's
word that xnch approved it." Validation is offline: RS256 signature check
against a cached key. The runner has no call path to xnch during normal
operation. A 401 from xnch is therefore never encountered during normal token
validation.

Impact: If xnch rotates its RS256 signing key (e.g., scheduled key rotation,
security incident response), the execution-runner has a stale public key and
will reject every subsequent execution token. The refresh trigger ("401 from
xnch") cannot fire via the documented path. There is no defined fallback, no
proactive key refresh schedule, and no alert condition for this failure mode.

R-5. DEFER Verdict Authorization Flow Is Undefined

Location: data-contracts.md (Policy Dry-Run Response) · execution-flow.md Step
  6 · decision-model.md (Policy Alignment Filter)

DEFER is a defined verdict with a requires_actor field. The documented
behavior is: DEFER options are "retained but marked, require secondary auth
before execution token issuance." The decision-model includes DEFER →
policy_score = 0.3.

No document defines: the endpoint for secondary authorization, the TTL for a
deferred action, what happens when secondary authorization is denied or times
out, how the secondary actor is notified, or whether a DEFER'd session can be
resumed after the primary session TTL expires.

Impact: DEFER is a defined contract value that will be returned to Nexi by
xnch. Nexi's behavior when it receives a DEFER for the highest-scoring option
is undefined. The operator cannot implement secondary authorization without a
path. A DEFER verdict currently functions as a soft BLOCK with no resolution
path.

R-6. Hold Record Has No Data Contract

Location: system-loop.md Failure Paths · execution-flow.md Steps 6, 8, 10 ·
decision-model.md

Every escalation path references "hold record written to xnch" and returns
hold_id and required_actor to the caller. No schema for the hold record exists
  in data-contracts.md or implementation-contracts.md.

Impact: Operators resolving escalations have no defined interface. The POST 
/audit/query path returns audit_ref but not hold records. The resolution
workflow — how an operator views, approves, or rejects a held request — is
entirely undocumented. ESCALATE is the failure mode for some of the
highest-risk decisions in the system; the resolution path for those decisions
is undefined.

R-7. GET /policy/check HTTP Method With JSON Request Body

Location: execution-flow.md Step 6 · xnch-control-plane.md Section 3.4 ·
data-contracts.md Step 6 inline contract

The policy dry-run is specified as GET /policy/check with a full JSON option
payload as the request body. HTTP GET requests with bodies are non-standard
(RFC 7231 §4.3.1: "A payload within a GET request message has no defined
semantics"). Many HTTP clients, proxies, and servers silently discard GET
bodies.

Impact: The parallel fanout of N GET /policy/check requests (up to 7 per
session) may silently fail if any component in the HTTP stack drops the body.
The policy engine would then evaluate an empty request and likely return a
default ALLOW verdict on all options — bypassing the entire policy filter.
This is the system's second-to-last policy gate before execution.

R-8. target_entity vs target_entity_id Field Naming Inconsistency

Location: data-contracts.md Intent schema · execution-flow.md Step 3 output ·
execution-flow.md Step 4 query

data-contracts.md Intent: "target_entity": "string".

execution-flow.md Step 3 output: "target_entity_id": "llama3-8b".

execution-flow.md Step 4 query body: "target_entity_id": "llama3-8b".

Impact: The field that Nexi emits from intent normalization (target_entity)
does not match the field the memory/read query uses (target_entity_id). One of
  the two is wrong. If the Intent object is passed directly to the Step 4 query
  builder, the query body would contain target_entity rather than
target_entity_id, and the episodic/pattern lookups would either fail or return
  empty results. This would cause every Step 4 query to retrieve no matching
episodes or patterns, causing the evaluator to use the 0.5 uninformed prior
for every outcome_score.

M-1. Clarification Routing Is Ambiguous Across Three Documents

Location: nexi.md §1.1 · execution-flow.md Step 3 ·
implementation-contracts.md Contract 7

- nexi.md: "Nexi returns a structured clarification request to xnch, which
routes it back to the originating actor."
- execution-flow.md Step 3: "Nexi returns CLARIFICATION_REQUIRED to input
layer with structured question."
- Contract 7: "xnch returns CLARIFICATION_REQUIRED to the caller."

These are three different routing descriptions. One makes xnch the routing
point; one makes Nexi the routing point; one makes the return channel
ambiguous. The clarification submission endpoint (POST 
/session/{session_id}/clarify, Contract 7) is also absent from the xnch
interface list in xnch-control-plane.md §3.

M-2. Event Log Retention (30 days) vs Decision Ledger (365 days) Asymmetry

Location: audit.md (configuration blocks)

Event Log retention: 30 days. Decision Ledger retention: 365 days. The full
forensic path described in decision-model.md — Decision Reconstruction uses
both trace_id (Event Log) and audit_ref (Ledger). For any decision older than
30 days, the Event Log sequence is gone. The Ledger entry exists for up to a
year, but the operational trace that contextualizes it does not. This degrades
  the audit quality for the majority of the Ledger's retention window.

---
M-3. No Tie-Breaking Rule for Equal Composite Scores

Location: decision-model.md — Decision Selector

The selection rule is "highest composite score." No tie-breaking is defined.
If two options produce identical composite scores (e.g., both 0.680), the
selected option is non-deterministic. Additionally, confidence = 
selected.composite - second_best.composite would equal 0.0, triggering the
low_confidence flag and potentially the human gate rule (Contract 7,
confidence < 0.10 + EXECUTION + irreversible). The audit trail for a
tie-broken selection would not explain why one option was chosen over another.

---
M-4. Recency Adjustment Applied Against Pre-Computed Aggregates

Location: decision-model.md — Outcome Score

The recency adjustment (7-day window, 1.5× weight) is described as applying to
  episodes "when computing success_rate." However, success_rate in the Pattern
Store is a pre-computed aggregate written every 6 hours. The live episodes
that fall within the 7-day window are not available at scoring time — only the
  pattern aggregate is. The mechanism by which recency weighting is applied to
a pre-computed aggregate field at query time is not defined.

---
M-5. Background Reconciliation Job Referenced but Never Defined

Location: execution-flow.md Step 14 · learning-loop.md (Outcome Collector) ·
implementation-contracts.md Contract 7

Three separate documents reference a "background reconciliation job" that
detects stale PENDING episodes. No component spec, schedule, process
definition, or trigger mechanism is provided. It is referenced as the safety
net for a specific failure mode (memory write failure at Step 14) but does not
  exist in the process map (runtime.md), the startup sequence, or the learning
loop component definition.

---
M-6. Score Adapter Monitoring Config Uses Wrong Dimension Names

Location: learning-loop.md monitoring YAML block

metrics:
  learning:
    dimension_accuracy:
      safety: true
      efficiency: true
      compliance: true
      context_fit: true

These names (safety, efficiency, compliance) match the Decision Ledger's
anomalous naming but not the actual evaluation dimensions (policy_score,
outcome_score, risk_score). Any monitoring dashboard built from this config
tracks metrics that are never emitted by the actual scoring pipeline. This is
a direct consequence of C-1 manifesting in the observability layer.
