  4. What Belongs Where

  architecture/ — Why the system is designed the way it is, what the major
  components are, how they relate, and what the non-negotiable boundaries are.
  No implementation detail. No SQL schemas. No code examples. No YAML configs.
  If it starts with "here is how to configure", it doesn't belong here.

  components/ — How to use, configure, and integrate each component. One file
  per deployable/instantiable component. The audience is the developer
  integrating against it. Describes inputs, outputs, configuration surface, and
  failure behavior. Not internal sub-module architecture.

  guides/ — Task-oriented walkthroughs. Answers "how do I accomplish X?". Each
  guide should be completable in isolation. The current set looks appropriate.

  reference/ — Exact, exhaustive, stable specifications. API contracts, CLI
  flags, data schemas, error codes. No prose explanation. Readers come here to
  look up a specific value, not to understand the system.

  ---
  5. Naming Conventions

  Current problems: near-identical names for files at different abstraction
  levels (nexi-decision-engine.md vs nexi-engine.md), inconsistent use of
  compound words vs hyphenation, and layer names (-layer, -system) used
  inconsistently.

  Adopt these rules:

  - Architecture files: named after the system or subsystem they describe.
  xnch-control-plane.md, nexi.md, memory-system.md. Drop -layer, -engine
  suffixes — those are implementation terms, not architecture terms.
  - Component files: named after the component as it would appear in code or 
  deployment. nexi-engine.md, execution-engine.md, audit.md.
  - Guide files: verb-noun format. policy-definition.md, backup-restore.md,
  model-setup.md. Current guides already follow this — keep it.
  - Reference files: noun or noun-noun. commands.md, endpoints.md, errors.md.
  Already consistent — keep it.
  - No index.md inside sub-directories should contain content — navigation
  pointers only.
