## 2. Per-source findings

### Source 1 — OpenEvolve (`github.com/algorithmicsuperintelligence/openevolve`)

**How the loop actually works.** The README documents the shape rather than the code: a controller cycles over an evaluator-scored program database organized as **island-based MAP-Elites** — config defaults `population_size: 500`, `num_islands: 5`, `migration_interval: 20`, ring-topology migration; feature dimensions (`complexity`, `diversity`, plus evaluator-supplied customs like `performance`) are auto-binned into a quality-diversity grid; "double selection" picks different programs for performance vs inspiration; sampling is multi-strategy (elite / diverse / exploratory). Iteration workers sample mutations via a weighted **LLM ensemble** (e.g. `gemini-2.5-pro` weight 0.6 / `flash` 0.4) with fallback; backends include any OpenAI-compatible `api_base`, Ollama/**vLLM locals**, optillm itself (`"moa&readurls-o3"`), and Claude Code CLI. Everything (LLM, database, evaluation) is seeded (`random_seed: 42`) for cross-machine reproducibility. `[ADOPT]` (as a reference architecture — the controller/database/worker shape is the mental model I'd reuse)

**Artifact side-channel.** Evaluators return `EvaluationResult(metrics={...}, artifacts={...})` where artifacts carry `stderr`, profiling data, `llm_feedback`, build warnings. OpenEvolve injects these into the *next generation's* mutation prompt as a "Previous Execution Feedback" section — "each generation learns from previous mistakes." This is the single most transferable idea in the repo-adjacent sense: my codegen migration should feed grader/compiler errors back into the next attempt's prompt as first-class context, not just as a retry. `[ADOPT]` (the pattern; no dependency needed)

**vLLM flag-space evolution — sanity check.** Treat `--kv-cache-dtype`, `--gpu-memory-utilization`, `--max-num-seqs`, `--cpu-offload-gb`, `--kv-offloading-size` as a genome and throughput/VRAM-headroom/context-length as fitness. Verdict: **this is the wrong tool for that space.** The genome is ~5-D with few legal values per dimension (fp8 is on/off; gpu-mem is a narrow continuous band; seqs is 1–4; offload-GB is a small integer grid) — a full or randomized grid is tens of runs. Each evaluation costs a vLLM restart (the systemd unit's `RestartSec` plus model load is minutes), so the bottleneck is evaluation count, which evolution does not reduce for a space this small; OpenEvolve's own positioning ("shines when you need to explore large solution spaces or optimize for multiple objectives") confirms the mismatch. MAP-Elites' diversity pressure has no interesting feature dimensions to exploit over 5 knobs. Script a sweep instead (see actions). `[NOT APPLICABLE — 5-D mixed grid; direct sweep strictly dominates on wall-clock and cost]`

**Prompt evolution for persona/weights.** The README's "evolve prompts instead of code" example (HotpotQA, +23% accuracy; details live in `examples/llm_prompt_optimization/`, not the README — treat the number as their claim, not independently verified) proves text genomes are first-class: the "program" is whatever files the evaluator is handed, and `evolve_function`/`run_evolution(initial_program=str, evaluator=callable)` make that explicit. `nexi/character/persona.yaml` and `nexi/weights/*.yaml` are exactly such text artifacts, and OpenEvolve runs fine against a local model via `api_base` — originally verified as "against LiteLLM `ornith`, zero cloud spend." **[drift update]** The serving model is now qwen-vl-7B for every default path (`nexi/config.py`, classifier), and ornith is only reachable by activating its unit (which deactivates qwen-vl). Two consequences: (a) persona evolution must target the model that actually serves production traffic — currently the 7B — or results optimize the wrong model; (b) if I evolve against ornith I must schedule unit-swap windows, and evolution quality on a 7B's prompt-space is likely flatter (less headroom, noisier mutations). The blocking prerequisite is unchanged and still first: an evaluator with a fixed eval set and a stable score; the repo currently has none (nexi's `Evaluator` scores decision options, not outputs). So: plausible, conditionally, after loop 2 exists. `[ADOPT]` — conditional on building the eval harness; cold-start today because no fitness-function scaffolding for prompts/outputs exists in-repo

**License / dependency footprint.** Apache-2.0, Python 3.10+, `pip install openevolve`; core dep list not enumerated in the README (one known internal: `dacite`). Since the "no heavy dependencies" rule isn't findable in `web/`, the binding convention is the repo's own prune-heavy-deps history — and OpenEvolve as a *CLI tool run offline* (not an import) keeps it out of the runtime dependency tree entirely. `[ADOPT]` (as a tool, not a library)

**Repo hook-in check:** no existing evaluator/fitness scaffolding this could attach to. `infra/no-k3s/e2e-test.sh` is a smoke test, not a benchmark. Integration is a cold start — the eval harness has to be built either way. `[NOT APPLICABLE — nothing to hook into; the harness is the actual work item]`

### Source 2 — optillm (`github.com/algorithmicsuperintelligence/optillm`)

**Placement.** optillm is an OpenAI-compatible *optimizing proxy in front of* a backend server: client → optillm (`:8000/v1`) → `--base-url` backend (env-prefixed `OPTILLM_*`). It exposes the same chat-completions surface it consumes ("drop-in replacement", "transparent proxy"). In default `--approach auto` mode, requests without a plugin slug pass through; composition with a router is mechanically fine because the surface is plain OpenAI. Direction caveat: the docs only *show* optillm wrapping the LiteLLM SDK or pointing downstream at a LiteLLM proxy; **LiteLLM → optillm is undocumented upstream** — it works because of the OpenAI surface, but I'd be off the documented path. `[ADOPT]`

**Between LiteLLM and vLLM, concretely.** Yes, without touching the existing `ornith` entry: run optillm (docker `latest-proxy` image is the lightweight variant) on Node B with `--base-url http://localhost:8082/v1 --approach auto --optillm-api-key <key> --host 0.0.0.0` (it binds 127.0.0.1 by default), then add one `model_list` block to `xnch/litellm_config.yaml`:

```yaml
- model_name: ornith-reasoned
  litellm_params:
    model: openai/cepo-ornith-1.0-35b   # slug prefix selects the technique per call
    api_base: http://192.168.50.2:8000/v1
    api_key: <optillm key>
```

The existing `ornith` route stays byte-identical. Verified against the current config: this is the one-line-insert case, not a refactor. **[drift update — this is now the big caveat]** `qwen-vl.service` declares `Conflicts=vllm-ornith.service`, so this route only works while ornith is the resident unit — and qwen-vl is now the default. An `ornith-reasoned` route in this topology isn't an always-on path, it's a *unit-swap decision*: serving it means either (a) a scheduled/mannually-flipped ornith window (systemctl stop qwen-vl → start vllm-ornith, ~minutes of load time each way), or (b) making the hard-reasoning tier an explicit operational mode. The insert stays one YAML block, but the claim "without disturbing the existing routing config" now understates it — nothing *routes* to ornith by default anymore, so adopting this means also re-adding an ornith branch to the classifier or a model-override path. Second-order caveat: techniques with n>1 sampling (CePO default best-of-3, MoA 3 upstream calls, `majority_voting` k=6) multiply upstream generations — originally ~3× serialized under `--max-num-seqs 1`, now ~1.5–2× under `seqs 2`; re-measure before quoting a number. vLLM supports n>1, so no technique is disqualified for that reason. `[ADOPT]` — but as an explicit operational mode, not a passive route

**Plugin syntax from LangGraph nodes.** Selection is per-request via `{slug}-model` prefix (hyphen, not colon — the prompt's `optillm:cepo-...` syntax does not exist), `extra_body={"optillm_approach": ...}`, or inline `<optillm_approach>` tags; `&` chains left-to-right (output of one stage feeds the next), `|` fans out in parallel and returns a list. Per-call invocation from a LangGraph node is therefore trivial (the model string is just a route parameter). But I'd still expose it as a *named route* ("hard reasoning") rather than free-form per-node slugs: the node picks `ornith` vs `ornith-reasoned`, and the reasoning-technique choice (`cepo`, `self_consistency`, `bon`) is a property of that route config, not scattered across graph code. Premise correction worth recording: **AutoThink, Deep Think with Confidence (deepconf), CoT-decoding, and entropy decoding are local-inference-server-only** — they need logits/steering and are "N/A for proxy." The prompt's interest in them via a proxy wouldn't work. `[ADOPT]` (as a route) / `[NOT APPLICABLE — AutoThink/deepconf specifically: unavailable through the proxy]`

**Memory plugin.** "Short term memory layer… unbounded context length with any LLM. Set `OPTILLM_MEMORY_FILE` to opt in to file-backed persistence." That is a fifth, inferior memory tier colliding with Redis sensory / Redis working / PG+pgvector episodic / Kuzu graph — different recall semantics, no routing policy, split-brain risk on the same conversations. As suspected: redundant, skip. `[NOT APPLICABLE — overlaps the four-tier stack; no integration path that doesn't fork memory truth]`

**License/footprint.** Apache-2.0, Python 3.10–3.12 in CI, `latest-proxy` docker image avoids the local-inference baggage entirely. `[ADOPT]`

### Source 3 — LangChain Deep Agents SDK (`docs.langchain.com/oss/python/deepagents/*`)

**Exact HITL mechanism.** `create_deep_agent(interrupt_on={...})` adds `HumanInTheLoopMiddleware` to the stack, and — direct quote — "Deep Agents support human-in-the-loop workflows **through LangGraph's interrupt capabilities**." Under the hood it is the same primitive I used in `pipeline_graph.py:select()`: pause via `interrupt()`, persist via a **checkpointer (explicitly REQUIRED)**, resume via `Command(resume={"decisions": [...]})` with typed decisions `approve | edit | reject | respond`, batching multiple pending tool calls into one interrupt. Two things they have that I don't yet: (a) `when`-predicate conditional interrupts (gate on tool *arguments*, e.g. only writes outside `/workspace/`), and (b) `PatchToolCallsMiddleware` repairing message history if a run is cancelled mid-approval. Filesystem-permission rules can also be declared `mode="interrupt"` and merge with `interrupt_on` into a single review step; subagents can override the parent's `interrupt_on`; tools may call `interrupt()` directly. Verdict on the narrative question: this **validates** the HITL gate — the reference harness converged on the same mechanism, which means my gate is idiomatic, not exotic; the differentiation vs. Apex is the *placement and completeness* (control-plane decision boundary + policy engine + audit ledger + default-deny second path in beeAI), not the existence of an interrupt. It also sharpens what I should claim: "hard interrupt at the actuation boundary, checkpoint-resumable, default-deny" — and I should be able to demo a resume, which today I can't (no `Command(resume=...)` in-tree). `[ADOPT]` (resume wiring + when-predicates + decision typing) / mechanism `[ALREADY PRESENT]`

**Virtual filesystem backends vs. the worktree pattern.** Backends: `StateBackend` (in-graph-state, thread-scoped, ephemeral), `FilesystemBackend` (real disk, `root_dir` + `virtual_mode=True` path jail), `StoreBackend` (LangGraph store, cross-thread), `CompositeBackend` (longest-prefix routing between backends — drafts in one, published to another), plus sandbox backends that add an `execute` tool; tool surface `ls/read_file/write_file/edit_file/delete/glob/grep`. `CompositeBackend` with a draft backend and a publish backend is *literally* draft-before-apply, in-process. But it is not a replacement for git worktrees: worktrees buy real git isolation — branches, diffs, the ability to run compilers/tests/`opencode` itself against the draft, and crash-safe cleanup — none of which an in-state filesystem provides. The right composition for the planned codegen loop: agent drafts into a StateBackend-scoped virtual FS (or CompositeBackend draft route), and *apply* is an explicit, HITL-gated materialization into a worktree where tooling runs. Complement, not conflict. Note honestly: neither half of that exists in the repo yet — `codegen_loop.py` and any worktree code are absent; MIGRATION_PLAN.md:208 claims a `composite_backend.py` that no longer exists. `[ADOPT]` (the composition shape) / `[NOT APPLICABLE — "replaces worktrees": no; worktrees remain the apply surface]`

## 3. Cross-source synthesis

**OpenEvolve + optillm as loop-4 mechanisms (the connection the four-loop framing predicts).** The article's loop 4 is "analysis agent over traces rewrites the harness." I already have the loop's skeleton: episodic traces → `pattern_extractor` → `policy_candidates` (an LLM analysis agent proposing policy-DSL rewrites) → human-governed application. What's missing are (a) a *fitness signal* and (b) rewrite targets beyond policy rules. That's precisely where the two ASI tools slot in, with a strict dependency order:

1. **Loop 2 first.** Neither tool can hill-climb without a grader. OpenEvolve's evaluator contract (`path → metrics`) and the article's rubric grader are the same object. 3. **OpenEvolve as the loop-4 *mechanism* for prompts.** With the eval harness in place, `persona.yaml` and `nexi/weights/*.yaml` become genomes; fitness = harness score (optionally blended with episodic success rates via the existing pattern store); the artifact side-channel carries grader errors into the next mutation — the same feedback discipline the article demands of loop 2, recycled as loop-4 signal.
